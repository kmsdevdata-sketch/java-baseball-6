### 기능 요구 사항 작성 
기능 요구 사항을 작성하였다 작성한 방식은 
요구사항 명세를 확인하며 요구사항을 기능별로 분리 -> 기능별로 분리된 요구사항에 맞춰 필요한 작업을 분리 -> 정확히 어떠한 요구사항에 맞는 기능인지 보정 

### 아쉬운점
- 기능요구사항을 분리할때 카테고리에 맞는 분류를 하면 더욱 한눈에 보기 편할듯함 (ex.출력,입력,기능 등등) 하지만 어떠한 보편적인 기준을 갖고 분리할지머릿속에 확립되지 않아 우선은 보았을때 불편하지 않을정도로만 분리하였음 
- 정확한 절차를 머릿속에서 떠올리기 어려움(정말 필요한 기능이 모두 작성되었는지 정확히 판별이 되지않음)
- 해당 기능에 필요한 테스트는 떠올려지지 않음
- 커밋메시지를 남길때 보편하된 메시지작성 방법을 익힐 필요가 있음

### 고민사항
- 어플리케이션 진입점을 main() -> run() 으로 잡았는데 게임 반복의 경계선을 잡는데 약간 헷갈려서 우선은 반복을 고려하지않고 한사이클이 제대로 이루어지도록 코드작성
- 기존에 Input,Output 을 분리하여 view를 구성하려 했지만  `camp.nextstep.edu.missionutils.Console`의 `readLine()`을 제공하고 + 사용자 입력분기가 많지 않기때문에 우선은 분리하지 않고 view로 통일
- 사용자의 입력값과 컴퓨터 랜덤값을 비교하여 결과를 산출하는 `evaluate()` 메서드가 현재는 결과값 스트링까지 만들고있는데 이는 메서드 역할이 중첩된걸로 판단되서 추후 개선이 필요할수 있다고 판단되고 3스트라이크인지 판별하기가 애매해져서 개선이 필요함
  - VO(GameResult)사용하여 명시적으로 스트라이크와 볼을 관리할수 있도록 변경하였음 
- 게임을 사용자가 맞힐때까지 반복가능한 구조로 설계까지는 완료했는데 사용자 입력에따라 재시작 분기를 3단 중첩 or 재귀호출 두개밖에 생각이 나지않음 아마도 `run()`의 구조 자체가 문제인거 같음 우선적으로는 중첩시키고 추후 개선

우선은 메서드로 목록을 뽑아본뒤 한 메서드내에서 두가지 이상의 기능을 할경우 분할가능한 범위를 잡아본다 
- 스트라이크 볼 갯수에 따라서 결과 알림 문자열을 파싱 
- 컴퓨터가 생성한 랜덤숫자와 플레이어가 입력한 숫자를 비교하여 스트라이크,볼 갯수를 구한뒤에 GameResult반환
  - 스트라이크/볼 갯수 구하기 
  - 스트라이크 GameResult 생성
- 플레이어가 입력한 문자열을 컴퓨터 랜덤수와 비교 가능하도록 List<Integer>로 변환 
- 랜덤숫자를 생성함
- 사용자가 3개의 수를 모두 맞히면 게임을 종료한다 
- 사용자가 2를 입력하면 게임을 종료 : 상태를 판별할수있는 별도 메서드가 좋아보임

#### 진행과정 
우선 뭐부터 해야될지 감이 잘안잡혀서 역할정리에 따라서 클래스/메서드 분리 -> 실행 -> 정상동작 -> 반복

#### 역할정리 - 지속 업데이트 
- Computer : 랜덤수를 생성 
  - 필드로 리스트형태의 `RandomNumbers` 를 갖게 하였음 - 불변성을 위해 final선언을 하여야 하나 싶었지만 추후 셔플 메서드를 통해 값변경이 필요하나 private 만 부여 
- Controller : 프로세스 실행순서 관리 
- View : 콘솔 입출력 
- GameResult : 스트라이크와 볼갯수(사용자 Guess결과) 의 의미를 담은 객체 
- Validator : 입력/결과 값 검사 
  - [x] 사용자가 수를 3개만 입력하였는지 
  - [x] 사용자가 문자열을 1~9 사이로 입력하였는지
  - [x] 사용자가 재시작여부 입력값을 1,2 둘중하나로 입력하였는지 
- Judge : 스트라이크 볼 판정을 함 

## 고민사항 
- Computer의 필드인 randomNumbers를 실행 컨텍스트 내에서는 불변해야하기에 final 선언할까 고민이 되었는데 재시작시에 shuffle이 되어야해서 우선적으로는 private만 부여함
- Judge의 `evaluate()` 가 GameResult를 반환하여도 괜찮을지 고민이 되었는데 DTO역할을 수행해도 문제는 없다고 판단하였음
- Judge가 스트라이크/볼에 따라서 결과 문자열 생성을 해도 괜찮을지 고민이 되었는데 유저입력값에 따른 결과값 생성에 대한 책임을 역할로 본다면 결과값 문자열 생성을 가져가도 문제없다고 판단하였음
- 기존 중첩 while문 기반 게임 반복실행을 do-while 문 사용및 메서드 분리를 통하여 분리하였는데 사용자가 게임을 다시하려할경우 shuffle() 을 해줘야하는데 시행위치가 애매함  
  - 1.`gameProcess()`시작부에 넣어준다 : 첫 진입시점에도 시행하여 이상함
  - 2.`wantsToPlayAgain()`에서 조건문 기반으로 넣어준다 : 기존의 메서드 역할인 사용자의 재시작여부를 묻는곳에서 셔플을 하게되어 메서드 역할 중첩 
  - 3.불변 참조 필드로 Computer를 사용하는게 아니라 메서드 내부에서 명시적으로 초기화 시킨다 : 참조범위 조정및 관리 코드가 늘어나서 그렇게 좋은 생각은 아닌듯함
  - 결론적으로 2번을 택하였음 이유는 1,3번에 비해 비교적 작성 근거가 명확하다고 판단 - 추후 명확한 상태관리가 이루어질수 있도록 리팩토링 필요할듯함

### 아쉬운점 
- 리팩토링시에 어떠한 순서 방법론에 따라서 진행할지 명확하지 않음 
- Controller에서 Computer를 필드 불변으로 사용하는데 "필드 불변으로 해야하는 이유" 에 대해서 정확히 설명을 내가 못한다는걸 깨닳음 + Application에서 주입받는 정확한 이유도
- Validator 를 만들어 구상한 입력검증 메서드는 모두 작성하였지만 검사시점이 Controller단에서 이루어져 예상하지 못한 예외가 터지는 경우가 있음
- 단순히 예외만 던지게 되어 의도한 예외가 나오긴 하지만 프로세스 흐름이 끊어져서 원만한 진행이 되지않음

  - `generateRandomNumbers()`: 호출시에 Computer 필드값인 RandomNumbers 가 할당되는지  
  - `generateRandomNumbers()`를 두번호출시에 첫번째 RandomNumbers 와 두번째 RandomNumbers 이 다른 필드를 가지고 있는지 - 이거는 애초에 테스트의미자체가 불안정하다고 판단해서 삭제 
  - 고민
    - `generateRandomNumbers()` 호출하여 필드값인 RandomNumbers 가 할당될때 RandomNumbers의 필드값이 실제 중복없는 랜덤값인지 검증을 해야하나? -> 우선은 코드상 실제 랜덤값인지 체크를 RandomNumbers 에서 하기때문에 일단은 그쪽으로 이전
    - "generateRandomNumbers를_두번호출하면_서로다른_RandomNumbers가_할당된다" 테스트에서 우연히 겹치는 수가 나올수도있는거니까 테스트를 만들긴했지만 좋은테스트는 아닌거같음  
- Judge:
  - `judge()` : 호출시에 설정해둔 값에맞게 스트라이크/볼 갯수가 포함된 GameResult가 반환되는지 
  - `isOut()` : 호출시에 GameResult의 스트라이크가 3개면 true , 아니면 false가 반환되는지 
  - `makeCallSign()` : 호출시에 설정해둔 값에맞게 스트라이크/볼 갯수가 포함된 문자열이 반환되는지 
  - 고민
    - `judge()` 에서 Computer,Player의 필드값이 비어있으면 예외처리를 하는 테스트,예외처리가 필요한가? -> 우선은 Computer,Player에서 각각 보장하는게 맞다고 판단하였음 Computer가 초기화시에 필드값을 가지고있지 않은 불완적 객체인게 문제라면 설계수정을 통해 초기화시에 명확히 값을 가지고있도록 수정이 필요하다고 판단 
- Player:
  - `create()`: 올바른 3자리수를 입력할시에 Player클래스 필드인 RandomNumbers 초기화가 정상적으로 이루어지는지 
  - `create()`: 올바르지 않은 값(실제 테스트코드 작성하면서 경우를 상세히 나눠볼 예정)을 입력시에 정상적으로 예외처리가 이루어지는지 
    - 3자리수가 아닌 입력
    - 각 자릿수가 정수 1~9에 속하지 않는 경우 
  - `convertPlayerNumbersToIntegers()` : 문자열 입력시 List<Integer> 형태가 정상적으로 반환되는지 - 해당 메서드가 헬퍼메서드며 `create()` 호출시 실행되기때문에 필드초기화가 제대로 이루어지는지 확인시에 같이 확인하는게 맞는거같음 
- Validator:
  - `validateNoDuplicates()`: 3자릿수가 넘는값을 넣었을때 예외를 던지는지 
  - `validateRestartNumber()`: 1~9가 아닌 자릿수(0)을 넣었을때 예외를 던지는지 
- RandomNumbers:
  - `create()`: 중복된값이 있는 List<Integer>를 넣었을때 예외를 던지는지 


#### 고민사항 
테스트코드 계획을 잡아보면서 느낀 현재 코드 설계상 애매한점이나 모르겠는점 - 나쁘다면 왜 나쁜지 좋다면 왜 좋았던건지 확인해보자 
- Player,Computer의 `getRandomNumbers()` 실제 컨트롤러에서 사용시에 getRandomNumbers().randomNumbers()와 같은 호출을 피하기 위해 Player,Computer모델에서 직접적으로 List<Integer>시그니처의 메서드를 만들었는데 해당 설계가 오히려 복잡성을 올리는지 모르겠음
- judge메서드가 정확하게 판단을 하는지 확인하기위해선 컴퓨터,플레이어 의 랜덤값을 제어 가능해야하는데 현재는 별도로 제어 가능한 방법이 없음 
  - 정확한 문제는 현재 Computer가 랜덤숫자 생성,보관을 모두 책임지는데 이때 생성에 대해 너무 자세히 알아버려서 문제인것같음 조금더 생각을 해보면 플레이어와 컴퓨터가 동일한 RandomNumbers 라는 필드를 갖고있는게 맞을까?
  - Computer가 랜덤숫자의 생성,보관을 책임지는건 괜찮음 - 하지만 랜덤숫자를 어떻게 생성하는지까지 알게되어 문제가 생김 추상화 계층을 추가해서 "랜덤숫자 생성"이라는 인터페이스를 사용하는듯한 형태로 바꿔주면 좋을듯함 랜덤숫자생성이라는 동일한 시그니처를 갖는 구현체로 
- Validator 가 입력값 검증을 하는것 자체는 괜찮은데 유틸성으로 사용되는 검증메서드가 아니라 도메인규칙을 띄우고 있는 검증과정이 있는것으로 판단되서 수
